# Checkpoint

## Design
- Mode: FastAPI greenfield, Python 3.10.16, FastAPI 0.110.0, direct `mysql-connector-python` persistence.
- Single cohesive Ticket/InternalNote domain group; reports are ticket repository queries, so it is implemented as one resource group to retain a single repository contract.
- Layers: Pydantic DTO schemas → thin routers with `Depends()` → `TicketService` → repositories → MySQL connection helpers.
- Service port: 8000. Compose infrastructure: `mysql:8.0.40`; app connects via `mysql` hostname in Compose.
- No authentication, messaging, seed data, or standalone testing framework. Pagination does not apply because no collection-list endpoint is requested.
- Error envelope: `{error: {code, message, timestamp, correlation_id}}`; request correlation middleware and centralized domain/validation/unhandled handlers.

## Brownfield feedback extension design
- Authentication remediation: protected feedback routes and ticket creation use a real `X-API-Key` credential. `AUTH_API_KEYS` is a required JSON object mapping opaque API keys to `{id, role}` server-side identities; the application uses constant-time key comparison and never trusts client identity/role headers. Roles are `customer`, `agent`, and `supervisor`, with centralized 401/403 domain errors. Ticket creation is customer-only and derives `customer_id` exclusively from the authenticated principal; clients cannot supply it.
- Existing tokens/identities are configuration, not database records: local Compose receives a non-production `AUTH_API_KEYS` mapping only for runnable verification, while operators must replace it with secrets in deployment.
- Feedback is one cohesive domain group: `feedback` owns the one-to-one ticket record, submission transaction, satisfaction aggregate, and two supervisor review queries. The SQL schema enforces `UNIQUE(ticket_id)` and uses a transaction-safe insert. DTOs live in `app/schemas.py`; endpoint handlers stay in `app/feedback.py`; persistence lives in `FeedbackRepository` and rules in `FeedbackService`.
- Feedback routes: customer `POST /tickets/{ticket_id}/feedback`; agent/supervisor `GET /agents/{agent_id}/satisfaction`; supervisor offset-paginated `GET /supervisor/low-rated-tickets` and `GET /supervisor/pending-feedback`. Each page uses a separate total query.
- Existing MySQL connection, error envelope, correlation middleware, FastAPI lifespan, port 8000, Docker image, and Compose MySQL are retained. The feedback table is initialized idempotently at lifespan startup.
